# 01 — Go

> Escribir Go **sin traducir Java**: qué hace el lenguaje en lugar de clases y herencia, qué patrones trae de serie, cuáles
> cambian de forma y cuáles desaparecen, y la trampa del *embedding* que se come a quien viene de Template Method.
> **Lenguajes:** Go, con Java al lado solo donde el contraste es el punto. Escrito contra **Go 1.27**, la última versión
> estable publicada en `go.dev` el día de la tanda; la versión de la corrida se fija en la revisión técnica. Asume leído
> [`01/06` — Herencia vertical y horizontal](../01-modelo-de-objetos/06-herencia-vertical-y-horizontal.md); el dominio es
> el de siempre (personas, documentos, cuentas).
>
> **Vigencia:** 2026-10-03.
>
> **Versiones ejecutadas:** Go 1.27.1 (2026-10-04).

## 1. 🎯 El problema

Un equipo que viene de Java escribe la validación de documentos como la escribiría allí, con un Template Method: una base
con el algoritmo y una "subclase" que redefine un paso. En Go, la "subclase" es un *struct* que **embebe** a la base:

```go
type ValidadorBase struct{}

func (v ValidadorBase) Validar(d Documento) error {      // el algoritmo: formato, luego vigencia
	if err := v.formato(d); err != nil {
		return err
	}
	return v.vigencia(d)
}
func (ValidadorBase) formato(d Documento) error  { return nil }   // el "gancho", sin comprobación
func (ValidadorBase) vigencia(d Documento) error { return vigente(d) }

type ValidadorPasaporte struct{ ValidadorBase }           // "extends"
func (ValidadorPasaporte) formato(d Documento) error { return comprobar(`^[A-Z]{2}\d{6}$`, d.Numero) }

err := ValidadorPasaporte{}.Validar(Documento{Numero: "123"})   // → nil: el pasaporte inválido pasa
```

- Compila, y el pasaporte `"123"` pasa la validación. `Validar` está declarado en `ValidadorBase`, y su receptor `v` **es**
  un `ValidadorBase`: `v.formato` llama al de la base, que no comprueba nada. El `formato` de `ValidadorPasaporte` no lo
  llama nadie.
- En Java, el despacho dinámico habría llamado a la versión de la subclase. En Go no hay despacho dinámico sobre tipos
  concretos: solo a través de **interfaces**.

Escribir Java en Go produce exactamente esto: código que parece correcto y que no hace lo que su autor cree.

## 2. 🧱 El modelo de objetos

**Qué hay.** Tipos con métodos, interfaces que se cumplen sin declararlo, y composición. La FAQ de Go responde a "¿es Go
orientado a objetos?" con un "sí y no": tiene tipos y métodos y permite ese estilo, pero **no hay jerarquía de tipos**.

```go
type Documento struct {                 // un struct: datos, sin constructores ni herencia
	Tipo        string
	Numero      string
	Vencimiento time.Time
}

func (d Documento) VigenteEn(fecha time.Time) bool {     // método con receptor por valor: recibe una copia
	return d.Vencimiento.IsZero() || !d.Vencimiento.Before(fecha)
}

type Validador interface {              // una interfaz: un conjunto de métodos
	Validar(d Documento) error
}

func NuevaPersona(nombre string, nacimiento time.Time) (*Persona, error) {   // el "constructor" es una función
	if nombre == "" {
		return nil, errors.New("nombre vacío")
	}
	return &Persona{nombre: nombre, nacimiento: nacimiento}, nil
}
```

- **Interfaces implícitas.** Un tipo cumple `Validador` si tiene el método `Validar` con esa firma; no lo declara en ninguna
  parte. La interfaz la define quien la **usa**, no quien la implementa: la guía de revisión de código de Go lo pide así.
- **Receptor por valor o por puntero.** `func (d Documento)` recibe una copia; `func (p *Persona)` puede modificar el
  original. Es la elección de [`01/01`](../01-modelo-de-objetos/01-identidad-estado-y-referencias.md) hecha explícita en cada
  método.
- **Visibilidad por mayúscula.** `Numero` se exporta fuera del paquete; `nombre`, no. El paquete es la unidad de
  encapsulación, no el tipo.
- **Sin sobrecarga, sin herencia, sin excepciones para el flujo normal.** El error es un valor que se devuelve.

**El *embedding*.** Un *struct* puede incluir otro tipo sin nombre de campo, y sus métodos se **promueven**: se pueden llamar
sobre el exterior. *Effective Go* lo dice con precisión: cuando se embebe un tipo, sus métodos pasan a ser métodos del tipo
exterior, pero al invocarlos el receptor es el tipo **interior**, no el exterior. Es reenvío automático, no herencia: no hay
despacho hacia "abajo", y por eso falló el §1.

## 3. 🧱 Lo que el lenguaje ya trae

| Necesidad | En Java | En Go |
|---|---|---|
| Adaptar un tipo a una interfaz | Una clase Adapter que la implementa | Nada si el tipo ya tiene los métodos; si no, un tipo función (`http.HandlerFunc`) |
| Inicializar una sola vez | Holder, DCL con `volatile` | `sync.Once`, o `sync.OnceValue` (desde Go 1.21) |
| Liberar un recurso | `try`-with-resources | `defer cerrar()` |
| Productor y consumidor | `BlockingQueue` | Un *channel* con capacidad |
| Cancelar trabajo en curso | Interrumpir, futuros cancelables | `context.Context` |
| Error esperado | Excepción *checked* | Un valor `error` devuelto |

- Los *channels* son el Producer-Consumer de [`10/03`](../10-concurrencia/03-producer-consumer-y-thread-pool.md) en el
  lenguaje: un *channel* con capacidad es una cola acotada, y enviar a uno lleno **bloquea** (contrapresión). *Effective
  Go* lo resume: no se comunica compartiendo memoria; se comparte memoria comunicando.
- `sync.OnceValue` devuelve una función que ejecuta la inicialización una sola vez, segura entre hilos: el
  [`10/06`](../10-concurrencia/06-inicializacion-perezosa-segura.md) entero en una línea, sin DCL que escribir mal.

```go
var catalogoTipos = sync.OnceValue(func() *CatalogoTipos { return cargarCatalogo() })

tipos := catalogoTipos()               // la primera llamada carga; las demás devuelven lo mismo
```

## 4. 🔀 Los patrones que cambian de forma

**Builder → *functional options*.** Go no tiene sobrecarga ni parámetros con nombre. En lugar de un Builder
([`04/03`](../04-creacionales/03-builder.md)), el constructor recibe opciones, que son funciones que configuran un campo:

```go
type OpcionCuenta func(*Cuenta)

func ConLimiteDiario(d Dinero) OpcionCuenta { return func(c *Cuenta) { c.limiteDiario = d } }
func ConTipo(t TipoCuenta) OpcionCuenta     { return func(c *Cuenta) { c.tipo = t } }

func NuevaCuenta(id CuentaId, titular PersonaId, opciones ...OpcionCuenta) *Cuenta {
	c := &Cuenta{id: id, titular: titular, tipo: Ahorros}       // valores por defecto
	for _, op := range opciones {
		op(c)
	}
	return c
}

cta := NuevaCuenta("CTA-0003", luis, ConTipo(Ahorros), ConLimiteDiario(Cop(200_000)))
```

- Lo obligatorio va como parámetro; lo opcional, como opción con nombre. Añadir una opción no rompe a nadie. Lo que no da:
  validar combinaciones de opciones antes de construir, que el Builder hace en `build()`; aquí se valida al final de
  `NuevaCuenta`.

**Template Method → el paso como interfaz.** La salida del §1 es componer: el algoritmo recibe el paso que varía.

```go
type ReglaFormato interface{ Formato(d Documento) error }

type ValidadorDocumento struct{ regla ReglaFormato }       // el paso, inyectado

func (v ValidadorDocumento) Validar(d Documento) error {
	if err := v.regla.Formato(d); err != nil {           // despacho por interfaz: llama a la regla real
		return err
	}
	return vigente(d)
}
```

- Es el Template Method convertido en Strategy ([`06/01`](../06-comportamiento/01-strategy.md)), que es lo que Go permite
  y lo que la composición recomendaba de todos modos.

**Decorator → *middleware*.** `func(http.Handler) http.Handler`: una función que recibe un manejador y devuelve otro que lo
envuelve. La cadena de auditoría y autenticación de un servidor HTTP en Go es una pila de Decorators escrita como
funciones.

**Producer-Consumer y Thread Pool → *channels* y *worker pool*.**

```go
func procesar(ctx context.Context, solicitudes <-chan Solicitud, trabajadores int) {
	var wg sync.WaitGroup
	for range trabajadores {                             // Go 1.22: range sobre un entero
		wg.Add(1)
		go func() {
			defer wg.Done()
			for {
				select {
				case s, abierto := <-solicitudes:
					if !abierto {
						return                           // el productor cerró el channel
					}
					ejecutar(ctx, s)
				case <-ctx.Done():
					return                               // cancelación
				}
			}
		}()
	}
	wg.Wait()
}
```

- Las *goroutines* son baratas, como los *virtual threads* de Java 21; el número de trabajadores lo pone el recurso escaso,
  igual que en `10/03`. `context` lleva la cancelación y el plazo a toda la cadena.

## 5. 🪦 Los patrones que desaparecen, y por qué

- **Singleton como clase.** Una variable de paquete y `sync.OnceValue`. No hay constructor privado que esconder: lo no
  exportado ya es privado del paquete.
- **Abstract Factory y Factory Method con jerarquías.** Una función `NuevoX(...)` que devuelve una interfaz cubre casi todo;
  sin herencia, no hay subclase a la que delegar la creación.
- **Iterator como objeto.** `for range` sobre *slices*, mapas y *channels*, y desde Go 1.23 sobre funciones iteradoras
  (`iter.Seq`): el recorrido perezoso se escribe como una función.
- **Visitor.** Un *type switch* (`switch d := x.(type)`) recorre las variantes. Lo que se pierde frente al `switch` sellado de
  Java 21: **Go no comprueba la exhaustividad**, y una variante nueva sin su caso cae en el `default` sin aviso.

## 6. 🩺 Las trampas

**El *embedding* no despacha como un override.** Es el §1. **Por qué parece correcto**: la sintaxis de llamada es la misma
que en Java, y los métodos promovidos se ven como heredados. **Lo que lo rompe**: un método de la base que llama a otro
método "suyo" llama siempre al de la base. **La corrección**: el paso que varía entra como interfaz (§4). **La
generalización**: en Go, el polimorfismo solo existe a través de interfaces; si el código depende de que alguien "redefina" un
método, está escrito en Java.

**La interfaz que no es `nil`.** Una interfaz guarda un tipo y un valor; la FAQ de Go lo explica en *"Why is my nil error
value not equal to nil?"*:

```go
func validar(d Documento) error {
	var err *ErrorFormato = nil          // un puntero nulo de un tipo concreto
	if !formatoValido(d) {
		err = &ErrorFormato{Numero: d.Numero}
	}
	return err                           // devuelve una interfaz con tipo *ErrorFormato y valor nil
}

if validar(cedula) != nil { /* entra siempre: la interfaz no es nil, porque tiene tipo */ }
```

- La corrección es devolver `nil` literal cuando no hay error: `return nil`.

**El receptor por valor que no modifica.** `func (c Cuenta) Depositar(m Dinero)` cambia una **copia**; el saldo del llamador
no se mueve. Lo que modifica, con receptor puntero.

**La *goroutine* que nunca termina.** Una *goroutine* esperando en un *channel* que nadie cierra queda viva para siempre: es la
fuga de memoria de Go. Cada *goroutine* necesita una forma de terminar: cerrar el *channel* o un `context` cancelado.

## 7. 🧭 Cómo se traduce

| Patrón o idioma de Java | Forma idiomática en Go |
|---|---|
| Herencia para reutilizar | *Embedding* para reenviar métodos; composición explícita para variar comportamiento |
| Template Method | El paso como interfaz o como función (Strategy) |
| Builder | *Functional options* |
| Adapter | Nada si los métodos ya coinciden; un tipo función o un *struct* que envuelve si no |
| Strategy, Command | Un tipo función (`type Regla func(Documento) error`) |
| Decorator | *Middleware*: una función que envuelve un manejador |
| Singleton, Lazy Initialization | Variable de paquete con `sync.OnceValue` |
| Visitor | *Type switch* (sin exhaustividad) |
| `BlockingQueue` y pool | *Channel* con capacidad y *worker pool* de *goroutines* |
| Excepción esperada | `error` devuelto como último valor |
| `try`-with-resources | `defer` |

**La frase en voz alta:** *"En Go no hay herencia: el *embedding* reenvía métodos pero el receptor sigue siendo el tipo
embebido, así que un Template Method escrito como en Java llama siempre al paso de la base. Lo que varía entra por una
interfaz, que se define donde se usa y se cumple sin declararlo."*

## ⚠️ Errores frecuentes

| Se dice | Lo preciso |
|---|---|
| "Go es orientado a objetos como Java" | Tiene tipos y métodos, pero no jerarquía de tipos; el polimorfismo es solo por interfaces |
| "El *embedding* es herencia" | Es reenvío: los métodos se promueven, pero el receptor es el tipo embebido y no hay despacho hacia el exterior |
| "La interfaz la declara quien la implementa" | Se cumple sin declararla, y la convención es definirla en el paquete que la usa |
| "Un `error` con un puntero nulo dentro es `nil`" | La interfaz tiene tipo y valor; con tipo, no es `nil` |
| "En Go se escribe un Builder" | Se usan *functional options*; el Builder se reserva para construcciones con pasos que validar |
| "El *type switch* es como el `switch` sellado de Java" | Go no comprueba la exhaustividad |
| "Las *goroutines* se limpian solas" | Una *goroutine* bloqueada para siempre es una fuga; necesita `context` o un *channel* cerrado |
