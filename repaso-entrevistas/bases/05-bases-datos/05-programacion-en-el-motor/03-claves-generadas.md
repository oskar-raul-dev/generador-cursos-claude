# 03 — Claves generadas

> Cómo genera cada motor sus claves —secuencias, `IDENTITY`, `AUTO_INCREMENT`, el `rowid` de SQLite—
> y qué cuesta usar un UUID en su lugar. Medido: un `ROLLBACK` deja un hueco en los tres motores;
> una secuencia desincronizada da una clave duplicada; SQLite reutiliza el identificador de una fila
> borrada; y un millón de UUIDv4 tardan 2,8 s en insertarse frente a 1,1 de un `bigint`, con un
> índice de 38 MB y las hojas a medio llenar. UUIDv7 lo deja en 1,8 s y 30 MB. **Asume leído:**
> [`03/01`](../03-el-motor-por-dentro/01-como-se-almacena-una-tabla.md) §6, donde la clave de InnoDB
> es la tabla, y [`03/02`](../03-el-motor-por-dentro/02-familias-de-indices.md), el B-tree.
> **Vigencia:** 27 de septiembre de 2026.

## 1. 🎯 El problema

La tienda numera sus pedidos con un entero que crece: `PED-00042` es el pedido 42. Tres cosas
sorprenden a quien lo mira de cerca. Los números **tienen huecos**, y contabilidad pregunta dónde
está el pedido que falta. Un día, tras una importación a mano, **el siguiente pedido falla** por
clave duplicada. Y cuando un segundo servicio empieza a crear pedidos sin preguntar a la base,
alguien propone **pasar a UUID**, «que no choca nunca».

Las tres cosas tienen la misma raíz: una clave generada no es un contador de negocio, es un
**identificador que el motor reparte deprisa y sin coordinar transacciones**. Este capítulo mide
cómo lo hace cada motor, dónde se rompe, y qué cuesta el UUID en el índice, que es la parte que casi
nadie mide antes de decidir.

> **📝 Contexto.** PostgreSQL y MySQL se corrieron en la copia aislada `bd-lab-prueba` de
> [`01`](01-funciones-y-procedimientos.md) —puertos 15432 y 13306, el MySQL vacío salvo las tablas
> que se crean aquí—; SQLite, en una base en memoria. Las tablas de prueba de cada sesión se crean y
> se tiran. **Longitud:** unas 480 líneas; capítulo denso, declarado en §4.6 de la guía de estilo:
> 193 líneas de sesión.

## 2. 🧱 Secuencias e `IDENTITY`

**Qué es:** una **secuencia** es un objeto que reparte números crecientes con `nextval`. Una columna
**`IDENTITY`** es la forma estándar de atarla a una tabla: `GENERATED BY DEFAULT` usa la secuencia
solo si no se da valor; `GENERATED ALWAYS` rechaza el valor que se dé, salvo que se fuerce.

**Quién lo manda:** `IDENTITY` es del **estándar**, y PostgreSQL la implementa sobre una secuencia;
el antiguo `serial` es una abreviatura propia. La documentación avisa de lo que importa: **un valor
de `nextval` no se recupera si la transacción aborta**, así que abortos y caídas dejan huecos.

```text
tienda=# CREATE TABLE prueba_id (id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, nota text);
CREATE TABLE
tienda=# INSERT INTO prueba_id (nota) VALUES ('uno'), ('dos');
INSERT 0 2
tienda=# BEGIN;
BEGIN
tienda=*# INSERT INTO prueba_id (nota) VALUES ('se deshace');
INSERT 0 1
tienda=*# ROLLBACK;
ROLLBACK
tienda=# INSERT INTO prueba_id (nota) VALUES ('tres');
INSERT 0 1
tienda=# SELECT id, nota FROM prueba_id ORDER BY id;
 id | nota 
----+------
  1 | uno
  2 | dos
  4 | tres
(3 filas)

tienda=# INSERT INTO prueba_id (id, nota) VALUES (5, 'a mano');
INSERT 0 1
tienda=# INSERT INTO prueba_id (nota) VALUES ('cuatro');
ERROR:  duplicate key value violates unique constraint "prueba_id_pkey"
DETALLE:  Key (id)=(5) already exists.
tienda=# INSERT INTO prueba_id (nota) VALUES ('cinco');
INSERT 0 1
tienda=# SELECT setval(pg_get_serial_sequence('prueba_id', 'id'), (SELECT max(id) FROM prueba_id));
 setval 
--------
      6
(1 fila)

tienda=# INSERT INTO prueba_id (nota) VALUES ('seis');
INSERT 0 1
tienda=# SELECT id, nota FROM prueba_id ORDER BY id;
 id |  nota  
----+--------
  1 | uno
  2 | dos
  4 | tres
  5 | a mano
  6 | cinco
  7 | seis
(6 filas)

tienda=# INSERT INTO pedidos (id, codigo, cliente_id, estado, total, creado_en) VALUES (2000000, 'PED-2000000', 311, 'PAGADO', 1, now());
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETALLE:  Column "id" is an identity column defined as GENERATED ALWAYS.
SUGERENCIA:  Use OVERRIDING SYSTEM VALUE to override.
tienda=# DROP TABLE prueba_id;
DROP TABLE
```

- **El hueco del 3**: la transacción deshecha se llevó su número. La secuencia no espera a saber si
  la transacción confirma, porque entonces cada `INSERT` esperaría al anterior. Los huecos son el
  precio de repartir sin bloquear.
- **La desincronización**: el 5 se insertó a mano, la secuencia no se enteró, y el siguiente
  `nextval` dio 5 y chocó. Es lo que pasa tras una importación o una restauración parcial. El
  **`setval`** la pone al máximo; y fíjese que el `INSERT` fallido **también gastó un número**:
  `cinco` recibió el 6.
- **`pedidos.id` es `GENERATED ALWAYS`**: rechaza el valor a mano. Es la opción que evita la
  desincronización, y `OVERRIDING SYSTEM VALUE` es la puerta explícita para una migración.

> **Veredicto:** una clave generada tiene huecos por diseño. Si el negocio necesita una numeración
> sin huecos —facturas—, es otra columna, asignada con otro mecanismo y otro coste.

## 3. ⚖️ `AUTO_INCREMENT` y el `rowid` de SQLite

MySQL hace lo mismo con **`AUTO_INCREMENT`**, y también deja el hueco:

```text
mysql> CREATE TABLE prueba_auto (id BIGINT AUTO_INCREMENT PRIMARY KEY, nota VARCHAR(20));
Query OK, 0 rows affected (0.008 sec)

mysql> INSERT INTO prueba_auto (nota) VALUES ('uno'), ('dos');
Query OK, 2 rows affected (0.002 sec)
Records: 2  Duplicates: 0  Warnings: 0

mysql> START TRANSACTION;
Query OK, 0 rows affected (0.000 sec)

mysql> INSERT INTO prueba_auto (nota) VALUES ('se deshace');
Query OK, 1 row affected (0.000 sec)

mysql> ROLLBACK;
Query OK, 0 rows affected (0.000 sec)

mysql> INSERT INTO prueba_auto (nota) VALUES ('tres');
Query OK, 1 row affected (0.001 sec)

mysql> SELECT id, nota FROM prueba_auto ORDER BY id;
+----+------+
| id | nota |
+----+------+
|  1 | uno  |
|  2 | dos  |
|  4 | tres |
+----+------+
3 rows in set (0.000 sec)
```

- **El mismo 1, 2, 4.** La documentación de InnoDB añade que, según `innodb_autoinc_lock_mode`, las
  inserciones concurrentes pueden **intercalar** sus números, a cambio de no bloquear la tabla.

SQLite es distinto: una columna `INTEGER PRIMARY KEY` **es** el `rowid` de la tabla
([`03/01`](../03-el-motor-por-dentro/01-como-se-almacena-una-tabla.md) §7), y el siguiente valor es,
normalmente, el mayor en uso más uno:

```bash
/opt/homebrew/opt/sqlite/bin/sqlite3 :memory: < sqlite-rowid.sql
```

```text
tabla|id|nota
sin_auto|3|cuatro
con_auto|4|cuatro
```

- **`sqlite-rowid.sql`** crea dos tablas con clave `INTEGER PRIMARY KEY`, la segunda con
  `AUTOINCREMENT` detrás, inserta tres filas en cada una, borra la tercera e inserta una cuarta.
- **Sin `AUTOINCREMENT`, la cuarta recibe el 3**: el identificador de la fila borrada **vuelve a
  usarse**. Si algo fuera de la base guardaba «el pedido 3», ahora apunta a otro.
- **Con `AUTOINCREMENT`, el 4**: SQLite guarda el máximo usado en una tabla interna y no repite. Su
  documentación advierte de que cuesta CPU, memoria y disco, y de que «normalmente no hace falta».

> **Veredicto:** los tres motores dejan huecos; solo SQLite, además, puede **reutilizar** una clave
> borrada. Donde una clave se publica fuera de la base, eso importa más que el hueco.

## 4. 🩺 UUID como clave, medido

**Qué es:** un **UUID** es un identificador de 128 bits que cualquiera puede generar sin preguntar a
nadie, con una probabilidad de choque despreciable. La versión 4 es **aleatoria**; la versión 7
empieza por una **marca de tiempo** en milisegundos y sigue con bits aleatorios, así que los UUIDv7
generados después son mayores. Las dos versiones las define la RFC 9562; PostgreSQL 18 trae
`uuidv4()` y `uuidv7()` de serie.

**El coste que se mide**: en un B-tree, un valor aleatorio cae **en cualquier hoja**. Hay que tener
esa hoja en memoria, y cuando se llena se **parte en dos**, dejando dos hojas a medio llenar. Un
valor creciente cae siempre **en la última hoja**, que se llena entera antes de abrir otra.

Un millón de filas en tres tablas iguales salvo la clave, con un `CHECKPOINT` antes de cada carga
para medir el WAL que escribe cada una:

```text
tienda=# CREATE EXTENSION pgstattuple;
CREATE EXTENSION
tienda=# CREATE TABLE clave_bigint (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, relleno text);
CREATE TABLE
tienda=# CREATE TABLE clave_v4 (id uuid PRIMARY KEY DEFAULT uuidv4(), relleno text);
CREATE TABLE
tienda=# CREATE TABLE clave_v7 (id uuid PRIMARY KEY DEFAULT uuidv7(), relleno text);
CREATE TABLE
tienda=# CHECKPOINT;
CHECKPOINT
tienda=# SELECT pg_current_wal_lsn() AS antes \gset
tienda=# \timing on
El despliegue de duración está activado.
tienda=# INSERT INTO clave_bigint (relleno) SELECT 'x' FROM generate_series(1, 1000000);
INSERT 0 1000000
Duración: 1091,259 ms (00:01,091)
tienda=# \timing off
El despliegue de duración está desactivado.
tienda=# SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'antes')) AS wal_bigint;
 wal_bigint 
------------
 135 MB
(1 fila)

tienda=# CHECKPOINT;
CHECKPOINT
tienda=# SELECT pg_current_wal_lsn() AS antes \gset
tienda=# \timing on
El despliegue de duración está activado.
tienda=# INSERT INTO clave_v4 (relleno) SELECT 'x' FROM generate_series(1, 1000000);
INSERT 0 1000000
Duración: 2822,136 ms (00:02,822)
tienda=# \timing off
El despliegue de duración está desactivado.
tienda=# SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'antes')) AS wal_v4;
 wal_v4 
--------
 162 MB
(1 fila)

tienda=# CHECKPOINT;
CHECKPOINT
tienda=# SELECT pg_current_wal_lsn() AS antes \gset
tienda=# \timing on
El despliegue de duración está activado.
tienda=# INSERT INTO clave_v7 (relleno) SELECT 'x' FROM generate_series(1, 1000000);
INSERT 0 1000000
Duración: 1753,608 ms (00:01,754)
tienda=# \timing off
El despliegue de duración está desactivado.
tienda=# SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'antes')) AS wal_v7;
 wal_v7 
--------
 149 MB
(1 fila)

tienda=# SELECT i.indexrelname AS indice, pg_size_pretty(pg_relation_size(i.indexrelid)) AS tam, s.avg_leaf_density, s.leaf_fragmentation FROM pg_stat_user_indexes i, pgstatindex(i.indexrelid) s WHERE i.relname IN ('clave_bigint', 'clave_v4', 'clave_v7') ORDER BY i.relname;
      indice       |  tam  | avg_leaf_density | leaf_fragmentation 
-------------------+-------+------------------+--------------------
 clave_bigint_pkey | 21 MB |            90.01 |                  0
 clave_v4_pkey     | 38 MB |            71.09 |              49.85
 clave_v7_pkey     | 30 MB |            89.98 |                  0
(3 filas)
```

- **`\gset`** guarda el resultado de la consulta en una variable de `psql`, `:antes`, y
  **`pg_wal_lsn_diff`** resta dos posiciones del WAL: lo que escribió cada carga.
- **`pgstatindex`**, de la extensión `pgstattuple`, lee el índice entero y da su densidad —cuánto de
  cada hoja está ocupado— y su fragmentación —cuántas hojas no siguen el orden físico—.

| Clave | Carga | Índice | Hojas llenas | Hojas fuera de orden | WAL |
|---|---|---|---|---|---|
| `bigint` | 1,09 s | 21 MB | 90 % | 0 % | 135 MB |
| UUIDv4 | 2,82 s | 38 MB | 71 % | 50 % | 162 MB |
| UUIDv7 | 1,75 s | 30 MB | 90 % | 0 % | 149 MB |

- **UUIDv4 tarda 2,6 veces más** y su índice ocupa 1,8 veces el del `bigint`. La mitad del tamaño
  extra es que el UUID mide 16 bytes y el `bigint` 8; la otra mitad son las **hojas partidas**, al
  71 %, y la mitad de ellas fuera de orden, que es lo que hace más caro recorrerlo después.
- **UUIDv7 recupera casi todo**: hojas al 90 % y ninguna fuera de orden, como el `bigint`, porque
  también crece. Lo que no recupera es el ancho: 30 MB frente a 21, y 1,75 s frente a 1,09.
- **El WAL sube con el v4**: tras un `CHECKPOINT`, la primera vez que se toca cada página se escribe
  entera en el WAL, y el v4 toca muchas más páginas distintas.
- **Y esto con el índice en memoria**: 38 MB caben de sobra en los 256 MB de `shared_buffers`.
  Cuando el índice no cabe, cada inserción aleatoria puede ser una lectura de disco, y la diferencia
  crece. No se midió aquí (sin confirmar en este entorno).

> **Veredicto:** un UUID como clave cuesta ancho siempre y desorden si es aleatorio. UUIDv7 quita el
> desorden y deja el ancho; si la clave no tiene que generarse fuera de la base, un `bigint` sigue
> siendo más barato.

## 5. ⚖️ InnoDB: la clave es la tabla

En InnoDB la tabla **está guardada en el orden de la clave primaria**, y cada índice secundario
guarda la clave primaria entera, como midió
[`03/01`](../03-el-motor-por-dentro/01-como-se-almacena-una-tabla.md) §6. Medio millón de filas con
`AUTO_INCREMENT`, con 16 bytes aleatorios y con un UUID versión 1 reordenado, cada tabla con un
índice secundario sobre `cliente`:

```text
mysql> SET SESSION cte_max_recursion_depth = 1000000;
Query OK, 0 rows affected (0.000 sec)

mysql> CREATE TABLE clave_auto (id BIGINT AUTO_INCREMENT PRIMARY KEY, cliente INT NOT NULL, KEY (cliente));
Query OK, 0 rows affected (0.009 sec)

mysql> CREATE TABLE clave_v4 (id BINARY(16) PRIMARY KEY, cliente INT NOT NULL, KEY (cliente));
Query OK, 0 rows affected (0.006 sec)

mysql> CREATE TABLE clave_v1 (id BINARY(16) PRIMARY KEY, cliente INT NOT NULL, KEY (cliente));
Query OK, 0 rows affected (0.008 sec)

mysql> INSERT INTO clave_auto (cliente) WITH RECURSIVE s (n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM s WHERE n < 500000) SELECT n % 50000 FROM s;
Query OK, 500000 rows affected (1.569 sec)
Records: 500000  Duplicates: 0  Warnings: 0

mysql> INSERT INTO clave_v4 (id, cliente) WITH RECURSIVE s (n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM s WHERE n < 500000) SELECT RANDOM_BYTES(16), n % 50000 FROM s;
Query OK, 500000 rows affected (2.411 sec)
Records: 500000  Duplicates: 0  Warnings: 0

mysql> INSERT INTO clave_v1 (id, cliente) WITH RECURSIVE s (n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM s WHERE n < 500000) SELECT UUID_TO_BIN(UUID(), 1), n % 50000 FROM s;
Query OK, 500000 rows affected (1.554 sec)
Records: 500000  Duplicates: 0  Warnings: 0

mysql> ANALYZE TABLE clave_auto, clave_v4, clave_v1;
+-------------------+---------+----------+----------+
| Table             | Op      | Msg_type | Msg_text |
+-------------------+---------+----------+----------+
| tienda.clave_auto | analyze | status   | OK       |
| tienda.clave_v4   | analyze | status   | OK       |
| tienda.clave_v1   | analyze | status   | OK       |
+-------------------+---------+----------+----------+
3 rows in set (0.006 sec)

mysql> SELECT table_name, index_name, ROUND(stat_value * 16 / 1024, 1) AS mb FROM mysql.innodb_index_stats WHERE database_name = 'tienda' AND table_name LIKE 'clave%' AND stat_name = 'size' ORDER BY table_name, index_name;
+------------+------------+------+
| table_name | index_name | mb   |
+------------+------------+------+
| clave_auto | PRIMARY    | 16.5 |
| clave_auto | cliente    | 15.5 |
| clave_v1   | PRIMARY    | 20.6 |
| clave_v1   | cliente    | 22.6 |
| clave_v4   | PRIMARY    | 33.6 |
| clave_v4   | cliente    | 24.6 |
+------------+------------+------+
6 rows in set (0.001 sec)
```

- **`cte_max_recursion_depth`** sube el tope de vueltas de una CTE recursiva, que en MySQL es 1 000
  por defecto; la CTE genera el medio millón de filas. Es la misma sesión de §3, a continuación.
- **`RANDOM_BYTES(16)`** hace de UUIDv4: 16 bytes aleatorios. **`UUID()`**, según su manual, es un
  UUID **versión 1**, basado en el tiempo; **`UUID_TO_BIN(…, 1)`** lo pasa a 16 bytes y reordena sus
  partes para que la de tiempo alta vaya delante, así que crece como un UUIDv7.
- **`stat_value`** en `innodb_index_stats` es el tamaño en páginas de 16 KB; el cálculo lo pasa a
  MB.
- **La tabla con clave aleatoria**: el `PRIMARY`, que es la tabla, pasa de 16,5 a 33,6 MB, y tarda
  2,4 s frente a 1,6: las filas se insertan en medio y parten páginas.
- **El índice secundario también engorda**: de 15,5 a 24,6 MB, aunque su columna es un `INT`, porque
  cada entrada lleva colgada la clave primaria, 16 bytes en vez de 8. Es la regla de InnoDB, clave
  **estrecha y creciente**, medida.
- **La clave ordenada, versión 1 reordenada, tarda lo mismo que `AUTO_INCREMENT`**, 1,55 s, y solo
  paga el ancho: 20,6 y 22,6 MB.

## 6. 🧭 Cómo se elige

- **`bigint` con `IDENTITY` o `AUTO_INCREMENT`**, por defecto: la más barata en espacio y en
  inserción. Con `GENERATED ALWAYS` en PostgreSQL, para que nadie la desincronice.
- **UUIDv7**, cuando la clave tiene que existir **antes** de llegar a la base —un cliente móvil que
  crea pedidos sin conexión, varios servicios que generan identificadores, una fusión de bases— o
  cuando no se quiere publicar un número que dice cuántos pedidos hay. Paga el ancho, no el
  desorden.
- **UUIDv4 como clave, no**, salvo tablas pequeñas: el desorden de §4 y §5 es el precio. Si ya
  existe, se puede guardar como columna única y usar un `bigint` como clave interna.
- **Numeración de negocio sin huecos** —facturas—: otra columna, asignada con un contador que se
  bloquea, sabiendo que serializa las inserciones.

**Cuánto cuesta** equivocarse: una clave aleatoria en InnoDB duplica el tamaño de la tabla y engorda
todos los índices secundarios, y cambiarla después es reescribir la tabla y todas las claves
foráneas que la apuntan.

## 7. 📜 Estándar, motor y convención

> **📜 Estándar o motor.** `IDENTITY` y las secuencias están en el estándar SQL; no he verificado la
> cláusula. `AUTO_INCREMENT` es de MySQL y `AUTOINCREMENT` de SQLite. Las versiones de UUID las
> define la RFC 9562, que no es una norma de bases de datos.

| Afirmación | Categoría | PostgreSQL 18 | MySQL 9.7 | SQLite 3.53 |
|---|---|---|---|---|
| Un `ROLLBACK` deja un hueco | Motor | Sí: 1, 2, 4 | Sí: 1, 2, 4 | — |
| Un valor dado a mano desincroniza el generador | Motor | Sí, con `BY DEFAULT` | — | — |
| Se puede prohibir el valor a mano | Estándar | Sí, `GENERATED ALWAYS` | No | No |
| Una clave borrada se reutiliza | Motor | No | — | Sí, sin `AUTOINCREMENT`: el 3 |
| UUIDv7 de serie | Motor | Sí, `uuidv7()` | No: versión 1 reordenada | No |
| La clave primaria ordena la tabla | Motor | No | Sí, InnoDB | Sí, el `rowid` |
| Una clave aleatoria parte hojas del índice | Motor | Sí: 71 % de densidad | Sí: 33,6 MB frente a 16,5 | — |
| Los huecos no son un error | Convención | — | — | — |

**Convención, la que más se repite.** *«El UUID es la clave moderna»* — es la clave de quien
necesita generarla fuera de la base. Dentro, un `bigint` ocupa la mitad y crece; y si hace falta
UUID, el v7 evita casi todo el coste del v4.

## ⚠️ Errores frecuentes

| Se dice | Lo preciso |
|---|---|
| "Un hueco en los identificadores es un pedido perdido" | Un `ROLLBACK` se llevó el 3 en PostgreSQL y en MySQL, por diseño |
| "La secuencia sabe qué valores hay en la tabla" | Tras insertar el 5 a mano, el siguiente `nextval` dio 5 y chocó |
| "Un `INSERT` fallido no gasta número" | Lo gastó: el siguiente recibió el 6 |
| "SQLite nunca repite identificadores" | Sin `AUTOINCREMENT`, dio el 3 a la fila nueva tras borrar la 3 |
| "UUID y `bigint` cuestan lo mismo en el índice" | 38 MB frente a 21, y 2,8 s frente a 1,1 para un millón |
| "UUIDv7 es tan barato como un `bigint`" | Quita el desorden, no el ancho: 30 MB frente a 21 |
| "El UUID solo engorda la clave primaria" | En InnoDB, el secundario sobre un `INT` pasó de 15,5 a 24,6 MB |
