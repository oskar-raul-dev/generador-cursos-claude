# ☕ 100 preguntas de entrevista — Java 11 y Java 17

> Enfoque en lo que realmente preguntan a un senior: **qué cambió entre LTS**, por qué, y qué duele al migrar.
> Referencia: Java 8 → 11 → 17 (con menciones a 21 donde aporta contexto).
> **Dificultad:** 🟢 base · 🟡 estándar · 🟠 profundidad · 🔴 abierta o adversarial

---

## 🗓️ Parte 1 — Versiones, LTS y migración (1–14)

**1. 🟢 ¿Qué significa LTS y cuáles son las versiones LTS?**
Long Term Support: versiones con soporte extendido de parches y seguridad. Son Java 8, 11, 17, 21 y 25. Desde Java 9 hay una release cada seis meses, y una LTS cada dos años (antes cada tres). En banca solo se usan LTS, porque el ciclo de certificación no admite cambiar de versión cada semestre.

**2. 🟡 ¿Por qué tantas empresas se quedaron en Java 8 tanto tiempo?**
Por tres razones concretas: el sistema de módulos de Java 9 rompió código que usaba APIs internas (`sun.misc.Unsafe`, `com.sun.*`); se eliminaron módulos Java EE del JDK (JAXB, JAX-WS, CORBA), lo que rompió aplicaciones empresariales; y el cambio de licencia de Oracle JDK 11 generó incertidumbre legal hasta que se consolidaron las distribuciones OpenJDK (Temurin, Corretto, Zulu).

**3. 🟡 ¿Cuál es la diferencia entre Oracle JDK y OpenJDK hoy?**
El código es esencialmente el mismo. La diferencia es la licencia y el soporte: Oracle JDK tiene condiciones comerciales específicas según la versión, mientras que Temurin (Adoptium), Amazon Corretto, Azul Zulu o Red Hat build son distribuciones OpenJDK gratuitas con soporte. En AWS, Corretto es la opción natural y tiene soporte sin coste.

**4. 🟠 ¿Qué es JPMS y por qué casi nadie lo usa en aplicaciones?**
El sistema de módulos de Java 9: `module-info.java` declara qué se exporta y qué se requiere, con encapsulamiento fuerte real. Casi nadie lo adopta en aplicaciones porque el ecosistema (Spring, librerías) funciona bien con el classpath, migrar es costoso y el beneficio para una aplicación desplegada en contenedor es limitado. Donde sí importa es en el propio JDK y en `jlink` para runtimes mínimos.

**5. 🟡 ¿Qué es `jlink` y `jdeps`?**
`jdeps` analiza dependencias de un artefacto, incluido el uso de APIs internas — es la primera herramienta de una migración. `jlink` construye un runtime a medida con solo los módulos necesarios, reduciendo la imagen Docker considerablemente. `jdeprscan` complementa detectando APIs obsoletas.

**6. 🟠 ¿Qué se eliminó del JDK entre 8 y 11 y cómo lo resuelves?**
Los módulos Java EE: JAXB, JAX-WS, JAF, Common Annotations, y también CORBA y Java FX. Se resuelven añadiendo las dependencias externas equivalentes (`jakarta.xml.bind`, etc.). También desapareció el Applet API y, más adelante, el Security Manager quedó obsoleto. En una aplicación empresarial antigua, estas ausencias son el 80% de los errores de arranque tras migrar.

**7. 🟡 ¿Qué es el encapsulamiento fuerte y qué rompió en Java 16/17?**
Desde Java 16 el acceso por reflexión a internos del JDK está **denegado por defecto** (antes solo advertía). Esto rompe librerías que usaban `setAccessible` sobre clases internas: versiones antiguas de Lombok, algunos frameworks de serialización, herramientas de mocking. La salida temporal es `--add-opens`, pero es una deuda: lo correcto es actualizar la librería.

**8. 🟠 ¿Cómo planificarías la migración de un sistema bancario de Java 8 a 17?**
Por etapas, no de un salto: primero compilar con Java 8 pero ejecutar sobre 11 (a menudo funciona), después subir el target. Inventario con `jdeps` de APIs internas y dependencias desactualizadas. Cobertura de pruebas suficiente **antes** de tocar nada. Actualizar primero las librerías (Spring, Hibernate, Jackson) que ya soportan la versión destino. Validar rendimiento con carga real, porque el cambio de GC por defecto (Parallel en 8 → G1 en 9+) altera el perfil de latencia. Y desplegar por olas con posibilidad de volver atrás.

**9. 🟡 ¿Qué riesgos de rendimiento tiene migrar de 8 a 11/17?**
El principal es el cambio de recolector por defecto: Parallel GC optimiza throughput, G1 optimiza pausas. Una aplicación batch puede rendir algo peor con G1, y una interactiva mejor. También cambian comportamientos de `String` (compact strings desde 9, que reduce memoria) y la detección de contenedores. Conclusión: **mide con carga representativa**, no asumas mejora automática.

**10. 🟡 ¿Qué mejoras trajo Java 11 para contenedores?**
Reconocimiento de límites de cgroups: la JVM ve la memoria y CPU asignadas al contenedor, no las del host. Con `-XX:MaxRAMPercentage` dimensionas el heap como porcentaje del límite del contenedor. Antes de esto, era clásico que la JVM viera 64 GB del host, dimensionara el heap en consecuencia y el kernel matara el pod.

**11. 🟠 ¿Qué es la política de compatibilidad de Java y qué se rompe entre versiones?**
Compatibilidad binaria muy alta en APIs públicas: el bytecode antiguo suele ejecutarse. Lo que se rompe es el acceso a internos, las APIs eliminadas y el comportamiento de herramientas. El mensaje para un comité: el riesgo de migrar no está en tu código, está en **tus dependencias** y en lo que ellas hacían por debajo.

**12. 🟡 ¿Qué es `--release` y por qué es mejor que `-source`/`-target`?**
`--release N` compila contra la API **de esa versión**, no solo con esa sintaxis. Con `-source`/`-target` puedes usar accidentalmente métodos que no existían en la versión objetivo y fallar en ejecución. En un pipeline serio, siempre `--release`.

**13. 🟠 ¿Qué son las preview features y cómo las tratarías en un banco?**
Funcionalidades que se incluyen para recibir retroalimentación y pueden cambiar o desaparecer; requieren `--enable-preview` tanto para compilar como para ejecutar, y el bytecode queda ligado a esa versión exacta. En banca: **no en producción**, punto. Sí en pruebas de concepto para preparar la adopción cuando se estabilicen.

**14. 🔴 Si hoy empezaras un proyecto nuevo, ¿elegirías 17 o 21? Justifica.**
Java 21 si el ecosistema lo permite: virtual threads cambian el modelo de concurrencia para cargas IO-bound, pattern matching está completo, y el soporte llega más lejos en el tiempo. Java 17 si hay dependencias corporativas o herramientas que aún no lo certifican, cosa habitual en banca. La justificación honesta ante un comité es de riesgo y talento, no de entusiasmo técnico: elige la versión más nueva que tus dependencias y tu equipo de plataforma soporten oficialmente.

## 🔟 Parte 2 — Novedades de Java 9 a 11 (15–38)

**15. 🟢 ¿Qué es `var` y cuáles son sus límites?**
Inferencia de tipo para variables locales (Java 10). Solo aplica a locales con inicializador, índices de `for`, y recursos de try-with-resources. **No** aplica a campos, parámetros ni retornos. No es tipado dinámico: el tipo se fija en compilación.

**16. 🟡 ¿Cuándo usar `var` mejora la legibilidad y cuándo la empeora?**
Mejora cuando el tipo es obvio y largo (`var mapa = new HashMap<String, List<Movimiento>>()`). Empeora cuando el tipo no se deduce del lado derecho (`var resultado = procesar(x)`), porque obliga a navegar para saber qué tienes. Regla de equipo razonable: `var` solo cuando el tipo aparece literalmente a la derecha.

**17. 🟡 ¿Qué son las factorías de colecciones inmutables?**
`List.of()`, `Set.of()`, `Map.of()` y `Map.ofEntries()` (Java 9). Devuelven colecciones **inmutables** y optimizadas en memoria. Dos trampas: no aceptan `null` (lanzan NPE) y lanzan `UnsupportedOperationException` al modificar, lo que sorprende a quien esperaba una lista mutable. Complementos: `List.copyOf()` y `Collectors.toUnmodifiableList()`.

**18. 🟡 Diferencia entre `Collections.unmodifiableList` y `List.of`.**
`unmodifiableList` es una **vista** de solo lectura sobre una lista subyacente: si alguien modifica la original, la vista cambia. `List.of` crea una estructura genuinamente inmutable y desconectada. Para garantizar inmutabilidad real, `List.copyOf(original)`.

**19. 🟡 ¿Qué métodos nuevos tiene `String` en 11?**
`isBlank()`, `strip()` / `stripLeading()` / `stripTrailing()` (conscientes de Unicode, a diferencia de `trim()`), `lines()` (stream de líneas), y `repeat(n)`. `strip()` frente a `trim()` es una diferencia real: `trim` solo elimina caracteres con código menor o igual a espacio, `strip` respeta la definición Unicode de espacio en blanco.

**20. 🟠 ¿Qué es el cliente HTTP de Java 11 y cuándo lo usarías?**
`java.net.http.HttpClient`: soporta HTTP/2, WebSocket, llamadas síncronas y asíncronas con `CompletableFuture`, sin dependencias externas. Lo usarías en librerías o utilidades donde no quieras arrastrar un cliente de terceros. En una aplicación Spring, `RestClient` o `WebClient` ofrecen mejor integración con métricas, trazas y resiliencia.

**21. 🟡 ¿Qué mejoras trajo `Optional` en 9 y 11?**
`ifPresentOrElse`, `or` (encadenar alternativas perezosas), `stream()` (convertir a stream de cero o un elemento, muy útil en `flatMap`) y `isEmpty()` en 11. Siguen valiendo las reglas: como tipo de retorno, no como parámetro ni campo; y `orElseGet` en vez de `orElse` cuando el valor por defecto es costoso de calcular.

**22. 🟡 ¿Qué es `Collectors.flatMapping` y `filtering`?**
Colectores intermedios (Java 9) que permiten filtrar o aplanar **dentro** de un `groupingBy` sin crear colecciones intermedias. Resuelven el caso de agrupar y a la vez transformar o descartar elementos de cada grupo, que antes exigía dos pasadas.

**23. 🟡 ¿Qué añadieron los streams en Java 9?**
`takeWhile` y `dropWhile` (toman o descartan mientras se cumple un predicado, aprovechando el orden), `ofNullable` (stream de cero o un elemento), e `iterate` con condición de parada, que da un equivalente funcional al `for` clásico.

**24. 🟠 ¿Qué es `Flow` y la API de Reactive Streams en Java 9?**
Las interfaces estándar `Publisher`, `Subscriber`, `Subscription` y `Processor` que definen contrapresión (backpressure). El JDK solo aporta el contrato, no una implementación completa: la usan Reactor, RxJava y Akka para interoperar. Su valor es tener un lenguaje común entre librerías reactivas.

**25. 🟡 ¿Qué es `process API` mejorado en Java 9?**
`ProcessHandle` permite obtener PID, información del proceso, hijos y un `CompletableFuture` al terminar. Relevante cuando tu aplicación orquesta procesos externos — por ejemplo, invocar ffmpeg desde Java para generar previsualizaciones de video.

**26. 🟡 ¿Qué son los métodos privados en interfaces?**
Desde Java 9 una interfaz puede tener métodos `private` para compartir código entre sus métodos `default` sin exponerlo en la API. Resuelve la duplicación que aparecía cuando varios `default` compartían lógica.

**27. 🟠 ¿Qué es try-with-resources mejorado?**
Desde Java 9 puedes usar una variable `final` o efectivamente final ya declarada, en vez de declararla dentro del paréntesis. Mejora la legibilidad cuando el recurso viene de fuera.

**28. 🟡 ¿Qué es el diamante con clases anónimas?**
Desde Java 9 se puede usar `<>` al instanciar una clase anónima cuando el tipo es inferible, algo que antes estaba prohibido.

**29. 🟠 ¿Qué es Compact Strings y qué impacto tiene?**
Desde Java 9, `String` almacena internamente un `byte[]` con codificación Latin-1 cuando todos los caracteres caben, en vez de `char[]` UTF-16. Reduce sustancialmente la memoria de aplicaciones con muchas cadenas ASCII — es una de las mejoras más rentables de migrar y no requiere cambiar código.

**30. 🟠 ¿Qué es AppCDS y para qué sirve?**
Class Data Sharing de aplicación: precomputa y comparte metadatos de clases entre ejecuciones, reduciendo el tiempo de arranque y la memoria cuando hay varias JVM. Útil en contenedores con arranques frecuentes y en escalado rápido.

**31. 🟡 ¿Qué es Flight Recorder y por qué importa que sea gratuito desde 11?**
JFR es un perfilador de bajo impacto integrado en la JVM (sobrecarga de alrededor del 1%), apto para **producción**. Desde Java 11 es open source y gratuito. Con JDK Mission Control analizas asignaciones, GC, bloqueos, IO y excepciones. Es la primera herramienta que debe nombrar alguien que ha diagnosticado rendimiento en producción.

**32. 🟠 ¿Qué GCs aparecieron entre 8 y 11?**
G1 pasó a ser el predeterminado desde Java 9. En 11 llegaron ZGC y Epsilon (un GC que no recolecta, útil para pruebas de rendimiento y tareas de vida muy corta), y Shenandoah en distribuciones de Red Hat. CMS quedó obsoleto en 9 y se eliminó en 14.

**33. 🟠 ¿Qué es ZGC y cuándo lo elegirías sobre G1?**
Un recolector de pausas ultra bajas (submilisegundo) que escala a heaps enormes, con la mayor parte del trabajo concurrente. Lo elegirías cuando el requisito sea latencia p99 estricta con heap grande — por ejemplo, un servicio de autorización de transacciones. Coste: algo más de consumo de CPU y de memoria frente a G1. En Java 21 es generacional, lo que mejora mucho su eficiencia.

**34. 🟡 ¿Qué es Epsilon GC y para qué se usa realmente?**
Un recolector que asigna memoria y nunca libera: cuando se agota, la JVM termina. Sirve para pruebas de rendimiento donde quieres eliminar el GC de la ecuación, para detectar la tasa real de asignación, y para tareas efímeras que caben en memoria. No es para producción general.

**35. 🟡 ¿Qué es `jshell`?**
El REPL de Java (9), útil para explorar APIs, validar comportamiento de métodos y enseñar. En entrevista es buena señal mencionarlo como herramienta de verificación rápida en vez de escribir una clase con `main` para probar dos líneas.

**36. 🟠 ¿Qué mejoró en `CompletableFuture` en Java 9?**
`orTimeout` y `completeOnTimeout` (timeouts sin construirlos a mano con un scheduler), `delayedExecutor`, y mejoras en subclassing. El timeout integrado es el más relevante: antes era código repetitivo propenso a fugas de hilos.

**37. 🟠 ¿Qué cambió en la gestión de versiones de `Runtime.Version`?**
El esquema de versión pasó a `$FEATURE.$INTERIM.$UPDATE.$PATCH` y `Runtime.version()` permite consultarlo programáticamente. Relevante para código que ramifica por versión de JVM, algo común en librerías y agentes.

**38. 🔴 Tu aplicación migró a Java 11 y consume más memoria que antes. ¿Qué investigas?**
Primero confirma dónde: heap, metaspace o nativa. Metaspace crece respecto a PermGen y es ilimitado por defecto — conviene acotarlo. Si es heap, el cambio a G1 tiene distinto comportamiento de ocupación y de devolución de memoria al sistema que Parallel. Si es nativa, revisa buffers directos y el número de hilos. Y verifica el dimensionado por cgroups: una JVM que no ve el límite del contenedor se dimensiona mal. Diagnostica con JFR y métricas de JVM, no con suposiciones.

## 🆕 Parte 3 — Novedades de Java 12 a 17 (39–68)

**39. 🟢 ¿Qué es un `record` y qué genera automáticamente?**
Una clase portadora de datos, inmutable y transparente (Java 16). Genera constructor canónico, accesores con el nombre del componente (`nombre()`, no `getNombre()`), `equals`, `hashCode` y `toString`. Es implícitamente `final`, no puede extender otra clase y sus campos son `final`.

**40. 🟡 ¿Cuándo NO deberías usar un `record`?**
Cuando necesitas mutabilidad, herencia, o control fino sobre la representación interna. También hay fricción con JPA: una entidad requiere constructor sin argumentos y campos mutables para el proxy, así que los records sirven para **DTOs y value objects**, no para entidades gestionadas. Frameworks que dependen de convención `getX()` pueden necesitar configuración.

**41. 🟡 ¿Qué es un constructor compacto en un record?**
Un constructor sin lista de parámetros donde validas o normalizas antes de la asignación implícita: `record Money(BigDecimal monto, String moneda) { Money { if (monto == null) throw ...; } }`. Es el lugar natural para garantizar invariantes, y demuestra que un record puede ser un value object de verdad, no una estructura tonta.

**42. 🟠 ¿Los records son realmente inmutables?**
Son **superficialmente** inmutables: los campos son finales, pero si un componente es una `List` mutable o un array, el contenido sigue siendo modificable desde fuera. Para inmutabilidad real hay que hacer copias defensivas en el constructor compacto y devolverlas en los accesores. Nombrar este matiz es una respuesta de senior.

**43. 🟡 ¿Qué son las `sealed` classes/interfaces?**
Java 17: una jerarquía cerrada donde el autor declara qué tipos pueden extender o implementar (`sealed interface Pago permits Transferencia, Tarjeta, Efectivo`). Las subclases deben ser `final`, `sealed` o `non-sealed`. Aporta control de la jerarquía y, sobre todo, permite al compilador verificar **exhaustividad**.

**44. 🟠 ¿Qué combinación hace potentes a `sealed` + `record` + pattern matching?**
Producen tipos de datos algebraicos en Java: una jerarquía cerrada de portadores de datos sobre la que un `switch` puede ramificar con garantía de exhaustividad. Si añades un caso nuevo al `sealed`, todos los `switch` que no lo contemplen **dejan de compilar**. Eso convierte un riesgo de ejecución en un error de compilación, que es exactamente lo que quieres en un dominio financiero.

**45. 🟡 ¿Qué es una switch expression y en qué se diferencia del switch clásico?**
Java 14: el `switch` **devuelve un valor**, usa `->` sin fall-through accidental, permite múltiples etiquetas por rama y `yield` para bloques. Frente al clásico: sin `break` olvidados, exhaustividad verificada sobre enums y tipos sellados, y expresión asignable en lugar de sentencia con variable mutable.

**46. 🟡 ¿Qué es el pattern matching para `instanceof`?**
Java 16: `if (o instanceof Cuenta c)` declara y castea en un paso, con alcance inteligente (la variable existe donde el compilador sabe que la condición se cumple). Elimina el trío comprobar-castear-asignar que ensuciaba todo el código de despacho por tipo.

**47. 🟠 ¿Qué es el pattern matching para `switch` y en qué versión se estabilizó?**
Ramificar por tipo dentro de un `switch`, con guardas (`case Transferencia t when t.monto() > LIMITE ->`). Fue preview en 17 y 20, y se estabilizó en **Java 21**. Es importante ser preciso en la entrevista: en Java 17 está disponible solo como preview, y en banca eso significa no usarlo en producción.

**48. 🟡 ¿Qué son los text blocks?**
Java 15: literales de cadena multilínea con `"""`, con manejo automático de la indentación incidental. Útiles para SQL, JSON y plantillas embebidas, que antes eran concatenaciones ilegibles. Detalle práctico: `\` al final de línea evita el salto, y `\s` preserva espacios finales.

**49. 🟡 ¿Qué son los helpful NullPointerExceptions?**
Java 14 (activadas por defecto desde 15): el mensaje indica **qué** referencia fue nula en una cadena de llamadas ("Cannot invoke `Cuenta.getSaldo()` because `cliente.cuenta` is null"). Reduce drásticamente el tiempo de diagnóstico frente al NPE mudo de antes. Nota de seguridad: el mensaje puede exponer nombres de campos en logs, algo a considerar en entornos sensibles.

**50. 🟠 ¿Qué otras mejoras relevantes trae Java 17 para código empresarial?**
API de números aleatorios mejorada (`RandomGenerator` con familias de algoritmos), `instanceof` con patrones, sellado de clases, mensajes de NPE útiles, y la eliminación definitiva del Applet API. También queda obsoleto el Security Manager, algo que afecta a aplicaciones antiguas con políticas de seguridad JVM.

**51. 🟡 ¿Qué es `Stream.toList()` y en qué se diferencia de `collect(Collectors.toList())`?**
Java 16: `toList()` es más conciso y devuelve una lista **inmutable**; `Collectors.toList()` no garantiza el tipo ni la inmutabilidad (en la práctica devuelve `ArrayList` mutable). Trampa en migraciones: código que recolectaba y luego modificaba la lista empieza a lanzar `UnsupportedOperationException`.

**52. 🟡 ¿Qué es `Stream.mapMulti` (Java 16)?**
Una alternativa a `flatMap` que, en vez de crear un stream por elemento, empuja los resultados a un consumidor. Es más eficiente cuando cada elemento produce pocos resultados, porque evita la asignación de streams intermedios. Nicho, pero buena señal conocerlo.

**53. 🟠 ¿Qué es `record` pattern y en qué versión está?**
Descomponer un record directamente en el patrón: `case Transferencia(Cuenta origen, Money monto) ->`. Es **Java 21**, preview en 19-20. Junto con pattern matching de switch, completa el estilo de programación orientada a datos.

**54. 🟠 ¿Qué es la programación orientada a datos que promueve Java moderno?**
Un estilo complementario a la POO: modelar el dominio con datos inmutables y transparentes (`record`), jerarquías cerradas (`sealed`), y lógica en funciones que ramifican por patrón en vez de por polimorfismo. Es adecuado cuando el conjunto de tipos es estable y las operaciones cambian a menudo — exactamente el caso inverso al que favorece el polimorfismo clásico.

**55. 🟡 ¿Qué cambió en el `Security Manager`?**
Quedó obsoleto para eliminación en Java 17 (JEP 411). Afecta a aplicaciones que lo usaban para sandboxing, algo presente en algunos entornos empresariales antiguos. La alternativa moderna es aislamiento a nivel de proceso o contenedor, no dentro de la JVM.

**56. 🟠 ¿Qué es la Foreign Function & Memory API y por qué importa?**
Sustituto moderno de JNI para llamar a código nativo y manejar memoria fuera del heap de forma segura y controlada. Fue incubación/preview durante 17-21 y se estabilizó en Java 22. Importa para integraciones con librerías nativas (criptografía de un HSM, por ejemplo) sin la fragilidad de JNI.

**57. 🟡 ¿Qué es la Vector API?**
API en incubación para operaciones SIMD expresadas en Java, que el JIT compila a instrucciones vectoriales de la CPU. Interesante para cálculo intensivo (riesgo, valoración de portafolios). Sigue en incubación, así que no es para producción.

**58. 🟠 ¿Qué es `jpackage`?**
Herramienta (estable desde Java 16) para empaquetar una aplicación Java como instalador nativo del sistema operativo, con su propio runtime. Relevante para aplicaciones de escritorio internas, que en banca todavía existen.

**59. 🟡 ¿Qué mejoras de diagnóstico añadió Java 17 frente a 11?**
Eventos adicionales de JFR, mejoras en los mensajes de excepción, `-XX:+UseSerialGC` y demás GCs afinados, y la eliminación de opciones obsoletas que hacían fallar el arranque. Práctica recomendada al migrar: revisar los flags de JVM heredados, porque muchos ya no existen y la JVM se niega a arrancar.

**60. 🟠 ¿Qué hace `strictfp` y por qué dejó de importar?**
Forzaba aritmética de punto flotante estrictamente conforme a IEEE 754. Desde Java 17 (JEP 306) **todo** el punto flotante es estricto por defecto, así que la palabra clave quedó sin efecto. Buena anécdota para demostrar profundidad.

**61. 🟡 ¿Qué cambios hubo en `Files` y NIO entre 8 y 17?**
`Files.readString`/`writeString` (11), `Files.mismatch` (12), `Path.of`, y mejoras de rendimiento en varias operaciones. Para código empresarial, `readString`/`writeString` eliminan una cantidad sorprendente de código repetitivo con streams y charsets.

**62. 🟠 ¿Cuál es el charset por defecto desde Java 18 y por qué importa?**
Desde Java 18, UTF-8 es el charset por defecto en todas las plataformas (JEP 400). Antes dependía del sistema operativo, lo que producía el clásico bug de acentos que solo ocurría en el servidor. En 11 y 17 esto todavía no aplica, así que la recomendación sigue siendo **especificar siempre el charset explícitamente**.

**63. 🟡 ¿Qué es `Objects.requireNonNullElse` y otros ayudantes?**
Utilidades (Java 9+) para valores por defecto y validación (`requireNonNullElse`, `requireNonNullElseGet`, `checkIndex`). Pequeñas, pero reducen el código defensivo repetitivo y hacen los fallos más claros.

**64. 🟠 ¿Qué es `@Deprecated(forRemoval=true, since="...")`?**
Java 9 enriqueció la anotación para indicar desde cuándo y si se eliminará. Importa porque `jdeprscan` puede auditar tu base de código contra las APIs marcadas para eliminación, lo que convierte la migración futura en una tarea planificable en vez de una sorpresa.

**65. 🟠 ¿Cómo afecta Java 17 a Spring y a Hibernate?**
Spring Boot 3 **exige** Java 17 como mínimo, y Hibernate 6 también elevó su requisito. Es decir, la migración a Java 17 no suele ser una decisión aislada: viene acoplada a la migración del framework, con el cambio de `javax.*` a `jakarta.*` como coste principal. Plantearlo así ante un comité es más honesto que venderlo como un cambio de runtime.

**66. 🟠 ¿Qué ganas concretamente en código de negocio al pasar de 8 a 17?**
Menos código repetitivo y más seguridad en compilación: `record` para DTOs y value objects, `sealed` + `switch` exhaustivo para máquinas de estado y jerarquías de operaciones, text blocks para consultas SQL legibles, `var` donde aporta, NPEs que dicen qué fue nulo, y un GC por defecto mejor para servicios. Nada de eso es revolucionario por separado; junto, reduce notablemente el ruido.

**67. 🟠 Reescribe mentalmente una jerarquía de estados de transferencia con Java 17. ¿Cómo queda?**
`sealed interface EstadoTransferencia permits Iniciada, Autorizada, Enviada, Confirmada, Rechazada, EnDuda`, cada uno un `record` con sus datos propios (motivo de rechazo, referencia del proveedor, marca de tiempo). Las transiciones se resuelven con `switch` exhaustivo, de modo que agregar un estado nuevo rompe la compilación en todos los sitios que deben contemplarlo. En banca eso vale más que cualquier prueba.

**68. 🔴 Un compañero dice que records y sealed son "azúcar sintáctico irrelevante". ¿Qué respondes?**
Que el azúcar sintáctico que elimina código repetitivo tiene un efecto real: menos líneas donde equivocarse. Pero el argumento fuerte es otro: `sealed` + `switch` exhaustivo no es azúcar, es **verificación en compilación** de algo que antes solo se detectaba en ejecución o no se detectaba. Convertir un bug potencial de producción en un error de compilación es un cambio de categoría, no de estilo.

## 🧵 Parte 4 — Concurrencia, memoria y rendimiento (69–86)

**69. 🟡 ¿Qué opciones de concurrencia tienes en Java 17 y cuál eliges?**
Hilos de plataforma con `ExecutorService`, `CompletableFuture` para composición asíncrona, `ForkJoinPool` para divide y vencerás, y streams paralelos para transformaciones CPU-bound sin efectos de lado. En 17 todavía **no** hay virtual threads estables (llegan en 21), y eso condiciona el diseño: el modelo "un hilo por petición" sigue teniendo un techo caro.

**70. 🟠 ¿Cómo dimensionas un `ThreadPoolExecutor` y qué configuras siempre?**
Tamaño según el tipo de carga: CPU-bound cerca del número de núcleos, IO-bound mucho mayor según el tiempo de espera. Configura **siempre**: cola acotada (una cola ilimitada es un OOM diferido), política de rechazo explícita, nombres en los hilos (sin eso, un thread dump es ilegible), y métricas expuestas. Y cierra el pool al apagar la aplicación.

**71. 🟠 ¿Qué peligro tiene `parallelStream()`?**
Usa el `ForkJoinPool.commonPool` compartido por toda la JVM: una tarea lenta o bloqueante ahí degrada a todo lo demás, incluidas otras partes del framework. Además, solo conviene con muchos elementos, operaciones CPU-bound y fuentes bien particionables. Si necesitas paralelismo controlado, usa tu propio pool o `CompletableFuture` con executor propio.

**72. 🟡 ¿Qué es `CompletableFuture` y cómo manejas sus errores?**
Composición de tareas asíncronas (`thenApply`, `thenCompose`, `thenCombine`, `allOf`). Errores: `exceptionally`, `handle`, `whenComplete`. Trampa clásica: una excepción no manejada en una cadena se traga silenciosamente hasta que alguien llama a `join()`. Siempre define el executor explícitamente y un timeout con `orTimeout`.

**73. 🟠 Explica el modelo de memoria de Java y qué garantiza `happens-before`.**
Define cuándo un hilo ve las escrituras de otro. `happens-before` se establece por: liberar/adquirir un monitor (`synchronized`), escribir/leer un `volatile`, arrancar y unir hilos, y las estructuras concurrentes del JDK. Sin una relación happens-before, el compilador y la CPU pueden reordenar y un hilo puede no ver nunca un cambio, aunque "en la práctica" parezca funcionar.

**74. 🟡 ¿Qué garantiza y qué no garantiza `volatile`?**
Garantiza visibilidad y prohíbe cierto reordenamiento. **No** garantiza atomicidad: `contador++` sigue siendo leer-modificar-escribir. Uso correcto: banderas de estado y publicación segura de referencias inmutables. Para contadores, `AtomicLong` o `LongAdder` (mejor bajo alta contención porque distribuye el conflicto).

**75. 🟠 `synchronized`, `ReentrantLock`, `StampedLock`: ¿cuándo cada uno?**
`synchronized` por defecto: simple, con optimizaciones de la JVM y liberación garantizada. `ReentrantLock` cuando necesitas timeout, interrumpibilidad, equidad o varias condiciones. `StampedLock` para lecturas dominantes con lectura optimista, que es muy rápida pero requiere validar y no es reentrante — mal usado provoca bugs sutiles.

**76. 🟠 ¿Cómo funciona `ConcurrentHashMap` y qué operación atómica deberías usar?**
Segmenta internamente y usa CAS más bloqueos por nodo, permitiendo lectura sin bloqueo. Operaciones atómicas clave: `computeIfAbsent`, `merge`, `putIfAbsent`. Error frecuente: hacer `if (!map.containsKey(k)) map.put(k, v)`, que no es atómico aunque el mapa lo sea — la atomicidad es por operación, no por secuencia de operaciones.

**77. 🟠 ¿Qué es un deadlock y cómo lo previenes en código bancario?**
Espera circular por recursos. Prevención práctica: orden global de adquisición (bloquear cuentas siempre por id ascendente en una transferencia), `tryLock` con timeout, y secciones críticas mínimas que **nunca** contengan llamadas remotas. Detección: thread dump — la JVM identifica los deadlocks de monitores explícitamente.

**78. 🟠 ¿Qué es el false sharing?**
Dos variables independientes que caen en la misma línea de caché hacen que los núcleos invaliden la caché del otro al escribir, degradando el rendimiento sin ninguna contención lógica. Mitigación: `@Contended` (requiere desbloqueo con flag) o padding manual. Es un tema de nicho, pero conocerlo demuestra profundidad en rendimiento.

**79. 🟠 ¿Cómo diagnosticas un consumo del 100% de CPU en producción?**
`top -H` para identificar el hilo, convertir su TID a hexadecimal y buscarlo en un thread dump (`jstack`), o directamente un perfil de 60 segundos con JFR o async-profiler. Sospechosos: GC thrashing (revisa logs de GC), bucle de reintentos sin backoff, regex con retroceso catastrófico, o serialización descontrolada.

**80. 🟠 ¿Cómo diagnosticas una fuga de memoria?**
Histogramas periódicos (`jcmd GC.class_histogram`), heap dump automático con `-XX:+HeapDumpOnOutOfMemoryError`, y comparación de dos dumps separados en el tiempo analizando el árbol de dominadores en Eclipse MAT. Sospechosos habituales: cachés sin límite, listeners no dados de baja, `ThreadLocal` sin limpiar en pools de hilos, y cargadores de clase retenidos tras redespliegues.

**81. 🟡 ¿Qué es metaspace y en qué se diferencia de PermGen?**
Metaspace (Java 8+) almacena metadatos de clases en memoria **nativa**, no en el heap, y crece sin límite por defecto. PermGen tenía un tamaño fijo y provocaba el clásico `OutOfMemoryError: PermGen space`. El riesgo actual es el opuesto: una fuga de cargadores de clase consume memoria del sistema hasta que el kernel mata el proceso. Por eso conviene fijar `-XX:MaxMetaspaceSize`.

**82. 🟠 ¿Qué flags de JVM configurarías en un contenedor?**
`-XX:MaxRAMPercentage` en vez de `-Xmx` fijo (para que escale con el límite del pod), `-XX:MaxMetaspaceSize`, logging de GC (`-Xlog:gc*`), `-XX:+HeapDumpOnOutOfMemoryError` con ruta a un volumen, `-XX:+ExitOnOutOfMemoryError` si prefieres que Kubernetes reinicie limpio, y selección explícita de GC si el perfil lo justifica. Y deja siempre margen entre el heap y el límite del contenedor para la memoria no-heap.

**83. 🟠 ¿Cómo elegirías el GC para un servicio de autorización de pagos?**
Prioridad: latencia p99 estable, no throughput. G1 con `MaxGCPauseMillis` ajustado como punto de partida; ZGC si el heap es grande y las pausas de G1 siguen apareciendo en el p99. Y la parte que importa: **medir con carga real**, porque muchas veces la causa de las pausas no es el GC sino la tasa de asignación del código, y ahí la solución es reducir basura, no cambiar de recolector.

**84. 🟠 ¿Qué es el JIT y por qué importan los warm-ups?**
La JVM interpreta primero y compila a código nativo los caminos calientes (C1 y C2 en compilación por niveles). Por eso las primeras peticiones son mucho más lentas. Implicaciones prácticas: las pruebas de carga necesitan fase de calentamiento para ser representativas, y en Kubernetes un pod recién arrancado puede fallar el SLO si recibe tráfico completo de inmediato — se mitiga con readiness retardada o calentamiento sintético.

**85. 🟠 ¿Qué es el escape analysis?**
Optimización del JIT que detecta si un objeto no se escapa del método y puede entonces eliminar la asignación (scalar replacement) o el bloqueo (lock elision). Consecuencia práctica: crear objetos pequeños y locales es mucho más barato de lo que la intuición sugiere, lo que quita fuerza a muchas "optimizaciones" manuales de reutilización de objetos.

**86. 🔴 ¿Cómo harías un benchmark creíble en Java?**
Con JMH, nunca con `System.currentTimeMillis()` alrededor de un bucle. JMH maneja calentamiento, evita que el JIT elimine código muerto (con `Blackhole`), aísla el estado y reporta con estadística. Y la parte de criterio: un microbenchmark aislado rara vez predice el comportamiento del sistema completo — mide también de punta a punta con carga realista, que es lo que de verdad vive el usuario.

## 🧭 Parte 5 — Práctica, trampas y preguntas abiertas (87–100)

**87. 🟡 ¿Qué es el `hashCode`/`equals` de un record y qué implica?**
Se generan a partir de **todos** los componentes. Implicación: si un componente es mutable (una lista), el hash cambia al mutarlo y el record se pierde dentro de un `HashMap`. Otra razón más para las copias defensivas.

**88. 🟡 ¿Los records se serializan bien?**
Sí, y de forma más segura que las clases normales: la deserialización usa el constructor canónico, así que **se ejecutan tus validaciones**, a diferencia de la serialización clásica que reconstruye el objeto saltándose el constructor. Es una de las mejoras de seguridad menos conocidas.

**89. 🟠 ¿Cómo manejas dinero en Java 17?**
`BigDecimal` con escala y `RoundingMode` explícitos, o enteros en la unidad mínima. Envuélvelo en un `record Money(BigDecimal amount, Currency currency)` con aritmética que impida sumar monedas distintas. Nunca `double`, y nunca `new BigDecimal(0.1)` — usa el constructor de `String` o `valueOf`. En base de datos, `NUMERIC`/`DECIMAL`.

**90. 🟡 ¿Cómo manejas fechas y zonas horarias?**
`java.time`: `LocalDate` para fechas sin zona (fecha de nacimiento), `Instant` para momentos absolutos (registro de un movimiento), `ZonedDateTime` cuando la zona es parte del significado. Nunca `Date` ni `Calendar`. En banca, define explícitamente qué significa "el día de la operación", porque la fecha contable y el instante UTC no siempre coinciden.

**91. 🟠 ¿Qué trampas tiene `Optional` que sigue viendo en código senior?**
`get()` sin comprobar (equivale a un NPE con pasos extra), `Optional` como campo de entidad (no es serializable y complica JPA), `Optional` como parámetro (usa sobrecarga), y `orElse` con un valor costoso que se calcula siempre aunque haya valor presente — ahí va `orElseGet`.

**92. 🟠 ¿Qué diferencias prácticas hay entre `Stream` y una colección?**
Un stream no almacena datos, es de un solo uso, es perezoso hasta la operación terminal, y puede ser infinito. Consecuencias: no puedes reutilizarlo, y depurar es más difícil porque las operaciones intermedias no se ejecutan hasta el final. Truco útil: `peek` para inspeccionar, con la advertencia de que puede omitirse si el stream se optimiza.

**93. 🟠 ¿Cuándo un `for` clásico es mejor que un stream?**
Cuando hay efectos de lado, cuando necesitas el índice o salir temprano con lógica compleja, cuando el stack trace debe ser legible para depurar, y en rutas ultra calientes donde la abstracción se nota. Un equipo maduro no discute esto por estilo: usa el que comunique mejor la intención en cada caso.

**94. 🟠 ¿Cómo garantizas compatibilidad binaria en una librería interna?**
No elimines ni cambies firmas públicas; añade en vez de modificar; usa `default` en interfaces para extenderlas sin romper implementaciones; marca lo obsoleto con `forRemoval` y un plazo. Verifica automáticamente con herramientas como japicmp en el pipeline. En una organización con decenas de consumidores, esto no es cortesía: es lo que evita un despliegue coordinado imposible.

**95. 🟠 ¿Qué harías si una dependencia crítica no soporta Java 17?**
Por orden: buscar versión actualizada; buscar alternativa mantenida; aislar la dependencia tras una interfaz propia para acotar el daño; en último caso, ejecutar ese componente en un servicio separado con la versión antigua mientras se resuelve. Y documentar la excepción con fecha de revisión, porque estas cosas se eternizan.

**96. 🟠 ¿Cómo convences a un banco de migrar de Java 8 a 17?**
En su idioma: Java 8 sin soporte extendido es **riesgo de auditoría y de seguridad** (CVEs sin parche), el talento disponible prefiere versiones modernas, y los frameworks actuales (Spring Boot 3, Hibernate 6) ya no soportan 8, lo que significa quedarse sin actualizaciones de seguridad en toda la pila. Añade el beneficio medible de rendimiento y memoria en contenedores. Y propón migración por olas con una aplicación piloto, no un big bang.

**97. 🔴 ¿Qué te parece la cadencia de seis meses de Java?**
Argumento a favor: entrega incremental, cambios más pequeños y digeribles, retroalimentación temprana con preview features. Argumento en contra desde la realidad empresarial: nadie en banca migra cada seis meses, así que en la práctica el ciclo relevante sigue siendo cada dos años con las LTS, y las versiones intermedias sirven sobre todo para probar lo que vendrá. Ambas cosas son ciertas, y decirlo demuestra visión de industria.

**98. 🔴 ¿Qué funcionalidad le falta a Java que te gustaría tener?**
Respuestas defendibles: tipos de valor / clases primitivas (Project Valhalla) para eliminar el coste del boxing en colecciones y cálculo intensivo; nulabilidad expresada en el sistema de tipos como en Kotlin; y sintaxis más ligera para inmutabilidad derivada (`with`). Menciona que Valhalla lleva años en desarrollo precisamente porque preservar compatibilidad binaria en una plataforma de treinta años es extraordinariamente difícil — eso demuestra que entiendes las restricciones, no solo la lista de deseos.

**99. 🔴 ¿Cómo evalúas si tu equipo está usando bien las novedades del lenguaje?**
Señales sanas: DTOs como records, jerarquías de estado selladas con switch exhaustivo, `var` solo donde el tipo es evidente, SQL en text blocks, ausencia de `Date` y `Calendar`. Señales de alarma: records con listas mutables sin copia defensiva, streams de quince operaciones ilegibles, `var` en todas partes, y pattern matching preview en producción. La regla: las novedades deben reducir ruido, no añadir ingenio.

**100. 🔴 Java vs Kotlin para un backend bancario nuevo: ¿qué recomiendas?**
Kotlin a favor: nulabilidad en el sistema de tipos (elimina una categoría entera de bugs), data classes, corrutinas, menos código repetitivo, interoperabilidad total con Spring. Java a favor: talento mucho más disponible (decisivo en un banco que contrata continuamente), herramientas y soporte corporativo, y una brecha de expresividad que se ha reducido mucho con records, sealed y pattern matching. Recomendación defendible: Java 17+ como estándar por riesgo de talento y homogeneidad, con Kotlin permitido en equipos que ya lo dominan. Y lo importante: es una decisión **organizativa**, no de gusto técnico, y así hay que presentarla.
